# pango-riscv 最终时序优化版设计文档

> 本文档是 CPU 与配套系统的设计/验证技术文档，面向竞赛报告与评审。
> 本版对应 `rtl_v_time/` 中的最终上板优化设计：指令集、五级流水组织、
> 应用功能与验证方法延续原设计，面向紫光 FPGA 的实现根据 **PDS 时序报告、
> 关键路径分析和布局布线结果**进行重构与优化。早期 yosys 结果仅用于
> 设计阶段的定性判断，最终频率、资源和关键路径均以 PDS 报告为准。
> 写作原则：先讲行为逻辑（什么情况下系统做什么、为什么这样设计），再列
> 结构与参数；性能数据注明测量口径，区分原始架构、最终 RTL、裸 SoC
> 实现与完整板级应用，避免把不同版本和不同测试条件的数据混用。

## 1. 概述

本项目实现一颗 RV32IM_Zicsr 五级流水线 32 位 RISC-V CPU。原始设计采用
SystemVerilog，最终 PDS 实现使用对应的 Verilog-2005 交付件；配套 SoC
外设、片上存储器与完整的仿真验证体系，并以其为处理核心构建
工业串行通信（Modbus RTU）逻辑分析与故障诊断应用：监听 RS-485 总线上的
通信流量，由 CPU 完成帧切分、CRC 校验、协议解析、请求-回复配对与响应
时间统计，识别通信错误与设备超时，结果经串口输出。

设计优先级：应用演示能力优先、跑分其次。性能与功能优化优先服务总线监听
应用的吞吐率、诊断延迟与外设能力。

指标速览（口径见对应章节）：

- 官方 ISA 合规：riscv-arch-test RV32IM 47/47 通过
- 官方机器模式特权测试：riscv-tests rv32mi 适用 8 项全过
- 随机化验证：三层随机化测试各 100 个种子无一失败
- CoreMark v1.01：原始架构 10 次迭代共 3,232,509 仿真周期；最终时序
  优化版同一工作量共 3,450,027 周期，差异主要来自 load-use 互锁
- 紫光 PDS 最终实现：裸 SoC 报告 Fmax 99.0589 MHz；完整板级应用报告
  Fmax 83.3820 MHz，实际采用 80 MHz 时钟并完成上板验证（口径见 7.2/7.3）

## 2. CPU 微架构

### 2.1 流水线结构

经典五级流水：取指（IF）、译码（ID）、执行（EX）、访存（MEM）、写回（WB）。

数据相关采用分级前递与 load-use 互锁相结合的处理方式。MEM 级只向 EX
级前递已经寄存的非 load 结果（ALU 结果或 PC+4），WB 级提供完整写回数据，
另保留 WB→ID 同拍旁路以及 store 数据的 WB 前递。最终版不再把数据存储器
当拍读出的 load 数据组合前递到 EX：当 MEM 级 load 的目的寄存器与 EX 级
指令的源寄存器字段匹配时，年轻流水级等待，MEM/WB 继续推进，下一拍再由
WB 前递提供数据。检测对两个源寄存器字段保守进行，个别不实际使用相应
字段的指令也可能多等待一拍。该改动不改变指令结果，只改变拍级调度；
其目的是切断 PDS 报告中的“存储器读出→前递→分支比较→改向→取指地址”
长组合路径。存储器接口仍采用 valid/ready 握手，2.4 节的 load 地址预取
机制保持不变。

### 2.2 乘除法单元

RV32M 乘除法由独立的多周期单元承担，与 EX 级之间用
start/busy/done 握手。乘法两级寄存（便于 FPGA 上推断为 DSP，EX 级占 2 拍）；
除法为 radix-2 迭代（EX 级占 33 拍）。

等待期间采用部分停顿策略：冻结 IF/ID/EX 三级，MEM/WB 照常推进——已发出的
年长访存握手不受冻结影响，避免了"停顿期间挂死总线"的隐患。

### 2.3 分支预测与跳转

- 条件分支：2-bit 饱和计数器动态预测器（BHT）。方向在 IF/ID 两级使用：
  IF 级供 BTB 命中的分支判方向，ID 级供 BTB 未命中分支预取 pc+imm；
  EX 级验证并更新；误预测时从正确路径精确恢复。
- 取指级 BTB（迭代五）：64 项直接映射，pc 低位索引 + 高位 tag（索引 +
  tag 覆盖完整 pc，无假命中），每项存 32 位目标 + 类型位（分支/JAL）。
  查找与取指同拍流水：本拍以查找地址索引、结果寄存一拍，与该地址的
  指令到达 IF 级同拍使用——命中且（JAL 或 BHT 预测跳）时 IF 级直接
  改向，预测全对零气泡。登记在 EX 级解析后：实际 taken 的分支与 JAL
  写入，未 taken 不登记（方向仍由 BHT 把关）。JALR 不进表（返回由 RAS
  覆盖；间接跳转实测 0.18% 已否决）。
- 直接跳转（JAL）：BTB 命中时 IF 级零气泡；未命中（首次执行）在 ID 级
  直转，惩罚 1 拍。
- 函数返回：16 项返回地址栈（RAS）。ID 级预测返回跳转目标并弹栈，EX 级
  验证；误预测时撤销错误路径上的弹栈，精确恢复栈指针与原栈顶内容。
- 预测标记随流水线：IF 级已预测的指令带「已预测 + 预测目标」标记进
  IF/ID、ID/EX，ID 级不再重复改向（否则把已在正确路径上的取指冲掉）；
  EX 级统一比对实际方向与目标，不符即重定向纠正（兜底防线，覆盖 BHT
  在 IF→ID 之间被更新翻转、tag 截断/代码自修改等情形）。最终版将直接
  跳转目标提前到 ID 级计算，并用预计算候选值完成 IF 预测的 JALR 目标
  验证，避免目标加法器与完整地址比较串联；这些电路实现变化由 PDS 关键
  路径分析驱动，不改变上述预测与恢复流程（见 2.5）。
- 时序关键取舍：BTB/BHT 取指侧查找地址只跟踪顺序流与 IF/ID 级改向，
  不跟完整 pc_next——EX 级重定向/陷入/WFI 的控制锥很长（数据前递→分支
  比较→重定向），若纳入查找地址，查表+tag 比对会接在整条重定向锥之后
  成为最差路径（早期 yosys 定性分析的最长路径由 18 级增至 24 级；仅排除
  数据路径不够，门控信号仍拖着整个锥，为 22 级；换用不带 EX/陷入门控的
  请求信号后才回到 18 级。该级数只用于早期相对比较，不是最终 PDS 延迟）。
  代价：这三类改向的目标指令到达时无 IF 级预测（valid=0），回退 ID 级
  原路径（1 拍气泡，同 BTB 未命中）——误预测恢复与陷入本就稀少，收益
  损失可忽略。

设计取舍记录：曾评估用 gshare 全局历史替换本地 2-bit 预测器，三种配置
（GHR=8/256 表项、GHR=4/256 表项、GHR=4/1024 表项）在 CoreMark 上误预测
次数均高于本地 2-bit 预测器约 9%，周期数回退 0.3~0.5%——同一分支随全局
历史散到多个表项，每个上下文都要重新训练，训练稀释的代价超过全局相关性
带来的收益。结论为负收益，放弃该方向。

间接跳转目标预测方向经实测量化后放弃（与前述已采用的分支/JAL 取指级
BTB 不是同一事项）：tb 侧只读计数（不动产品 RTL，
按 idex_pc 从 imem 读回指令解码，tb_soc +BTBSTAT）实测 CoreMark 全程
「未预测间接跳转」（JALR 且 rs1 非 link 寄存器）重定向仅 3,362 次，
按每次 2 拍估算约占总周期 0.18%；应用固件两侧形态（demo 自检 25 万
周期、连续运行含命令接口 100 万周期）实测均为 0——间接跳转在本核
工作负载中几乎不存在（直接调用 JAL 译码级直转、返回由 RAS 覆盖），
间接跳转目标预测的收益上限不足以抵消面积与复杂度，不立项。

IF 级预测量化与落地（迭代五）：事前量化（tb_soc +PERFSTAT，只读计数
设施，不动产品 RTL；口径：统计 ID 级重定向——JAL 直转/分支预测 taken/
RAS 返回命中，预测全对也各付 1 拍气泡，取指级预测可消除；
!stall_young/!wfi_wait 门控防停顿与 WFI 睡眠期重复计数）为 CoreMark
全程 408,253 次 ≈ 总周期 11.13%（分支 taken 345,808 / JAL 27,818 /
RAS 返回 34,627），净收益上限约 10%；应用固件 busy 期口径约 15%
（连续运行形态 64.9% 周期在 WFI 睡眠，睡眠期无取指收益）。
落地后实测：CoreMark 10 迭代 3,547,147 → 3,232,509 周期（-8.87%）；
IF 级 BTB 预测改向 370,809 次（占总周期 11.07%），残余 ID 级重定向
44,105 次 ≈ 1.32%（RAS 返回 34,627 为主体，其余为 BTB 未命中与
作废路径的分支/JAL）；误预测次数 40,571→40,572 不变（恢复代价未
加深）；应用固件自检形态三场景（offline/normal/timeout）实测
-6.7%~-8.1%。RAS 前置（原第二步可选项）评估后放弃：残余 RAS 返回
气泡仅约 1.03%，且需把 EX 级撤销链延伸到 IF 级弹栈，收益不抵复杂度。
WFI 睡眠期门控已补齐（迭代五前置小修）：
此前睡眠期若 ID 级滞留预测 taken 的指令，id_redirect 会反复拉起（pc
被 wfi_wait 优先保持，无真重定向），滞留 ret 还会每拍空弹 RAS——
行为正确但 IF 空翻、RAS 预测精度受损；补 !wfi_wait 门控后睡眠期
不再空翻，唤醒响应确定性提前一拍（demo 故障日志两处事件时间戳
64155→64154，golden 已同步，架构行为不变）。

### 2.4 存储器子系统

哈佛结构，指令与数据存储器均为同步读 BRAM（Pango DRM 推断模板），CPU 核心
与存储器类型解耦。同步读天然引入一拍读延迟，两处针对性优化把代价消化掉：

- 指令口提前一拍送地址：取指地址在需要数据的前一拍就送给 BRAM，
  取指无性能损失。
- 数据口 load 预取：load 地址经预取口提前一拍预采样，命中时把 2 拍读
  缩为 1 拍；地址线被占用时回退 2 拍路径。外设握手时序不受影响。

store 拍 load 预取放开的收益实测量化（+PERFSTAT 同设施：统计 EX 级
load 预取因 MEM 级 store 占用数据口地址线而放弃的次数，每次回退 2 拍
路径白付 1 拍；复核后补充分类探针口径）：总上限 CoreMark 22,048 次
≈ 0.60%、应用 demo 自检形态 20,386 次 ≈ 8.15%、连续形态 0.10%——
但按可回收性拆开（「load 落 RAM 且与 store 不同字」才可回收：同字
须回退保正确性，外设 load 本就不吃预取）：可回收仅 CoreMark 19,867
次 ≈ 0.54%、应用自检 350 次 ≈ 0.14%、连续 992 次 ≈ 0.10%；应用自检
的 8.15% 里 98% 是同字对（编译器栈槽溢出/重载惯用法），要吃到须做
store→load 前递（MEM 级 store 数据直接给同字 EX 级 load）而非预取
放开。最终裁定：预取放开与前递均不立项——二者对 demo 判定物（UART
报告与 GPIO 告警，内容由硬件时间戳决定，与 CPU 快慢无关）无可见
影响，应用 CPU 算力占用仅数个百分点、瓶颈在 UART 打印与总线速率，
CoreMark 侧合计 0.60% 不抵复杂度。评估顺带坐实了一个既有缺陷：
dmem 读口在 store 拍采样写口同地址，构成双口 BRAM 硬冲突（仿真按
读旧值且读结果无人用所以从未暴露，真机行为未定义）——已由性能
迭代四修复：写拍读口采样地址翻到相邻字（字索引最低位取反）避开
冲突，冲突拍读数本就无人使用，行为逐拍不变（CoreMark 周期逐拍一
致、早期 yosys 定性最长路径 18 级不变）；tb_soc 常开不变式断言
「写拍读口采样字索引 ≠ 写地址字索引」防回归（对缺陷版负向验证确认会触发）。

### 2.5 面向紫光 PDS 的最终时序实现

本节记录最终代码相对原始架构的实现级调整。除 2.1 所述 load-use 互锁会
增加相关指令的等待拍外，本小节其余改动均不增加正常执行拍数，也不改变
指令集语义、异常优先级和外设接口。优化依据不是单纯的表达式推演，而是
**紫光 PDS 综合、布局布线后的慢路径清单、路径起点终点、逻辑/连线延迟
占比及多角时序报告**。

- **寄存器堆落实为触发器**：PDS 曾将行为描述的 32×32 寄存器堆映射为
  DRM。最终版显式实例化 `GTP_DFF_E`，x1～x31 共 992 位各保存一份，x0
  不分配存储状态；两个异步读口共享触发器状态，各经五层二选一平衡树读数。
  写回仍为同步写，WB→ID 旁路保持不变。该实现与紫光器件绑定，解决的是
  实际物理映射和寄存器堆输出路径问题，而不是增加流水级。
- **前递选择资格提前寄存**：两个源操作数的 WB 匹配位随 MEM/WB 数据同拍
  准备；MEM 前递的完整资格（写寄存器、非 load、目的编号非零、编号匹配、
  非气泡）随 EX/MEM 同拍准备。EX 级不再临时串联编号比较和资格判断，直接
  按 MEM > WB > 原操作数的优先级选择。全局等待、年轻级暂停及清流水拍采用
  与对应流水数据相同的更新规则，保证选择位与数据始终同拍对应。
- **分支目标计算和验证去串联**：JAL/条件分支的 `PC+立即数` 在 ID 级预先
  计算并随原有 ID/EX 寄存器下行；IF 级 BTB 命中的 JALR 目标验证改为比较
  两个由预测目标与立即数逆算的源寄存器候选值，奇数预测目标显式判不匹配。
  真实目标加法器仍保留用于重定向与异常现场，但不再挡在预测验证之前。
- **异常汇总控制并行化**：将原始 load/乘除等待、MEM 异常、EX 同步异常、
  中断与重定向候选尽量并行准备，MEM 异常直接进入总陷入请求，不再先改变
  load 等待、绕经年轻级控制后再返回 `trap_any`。陷入原因、现场地址与
  MEM 故障 > EX 异常 > 中断的优先关系不变。
- **宽数据与清流水控制解耦**：IF/ID、ID/EX、EX/MEM 中的 PC、操作数、
  立即数和预测目标等宽数据通常在暂停时保持（load-use 等待时为保留可用
  前递值而更新操作数除外）；清流水主要作废指令有效位、控制位和预测标志，
  无效拍的数据不参与提交。这样保持冲刷语义，同时减少
  清空控制对大量寄存器使能端的扇出。取指地址选择在外层已排除暂停、陷入
  和 EX 纠正的分支中直接使用原始 ID 改向请求，省去重复门控。
- **中断向量入口预计算**：写 `mtvec` 时同步缓存 MEI/MSI/MTI 三个已实现
  中断的向量入口（基址分别加 44、12、28）。vectored 中断发生时只选择
  对应寄存器，不再把“基址+中断编号×4”的 32 位加法放在陷入到取指的
  组合路径上；direct 模式和同步异常入口不变。

这些改动共同将复杂判断从关键拍移入已有的前级寄存边界，或减少公共控制
对宽数据路径的影响。它们属于功能等价的微架构/电路实现优化；最终是否
采用由 PDS 完整实现后的频率、资源和程序周期共同判断，而非仅凭 RTL
形式上的“路径变短”。

## 3. 异常与中断

### 3.1 设计定位

实现的是**仅机器模式（M 态）的最小异常/中断子集**（Zicsr），目标是覆盖
应用的中断驱动需求与官方 rv32mi 特权测试合规，**不是严格意义上的完整
异常/中断体系**——未实现项在 3.4 节逐条列明，阅读与引用时勿误读。

### 3.2 已实现机制

CSR 组：mstatus（仅 MIE/MPIE 可写，MPP 硬连 11）、
misa（RV32IM 常量，写按 WARL 忽略）、mie/mip/mtvec/mepc/mcause/mtval/
mscratch，以及 mvendorid/marchid/mimpid/mhartid 只读 ID 组（写尝试判非法
指令）。CSR 在 EX 级读改写，不存在 CSR 数据相关问题。

同步异常精确陷入，按发现位置分级触发：

- ecall(11)/ebreak(3)/非法指令(2)：ID 级发现，随标记到 EX 级触发；
- 非对齐 load/store(4/6)、未映射总线访问(5/7)：MEM 级触发；
- 分支/跳转目标非对齐(0)：EX 级触发（跳转撤销，link 不写回）。

mtval 按异常类型记录指令编码、访存地址或目标地址。陷入优先级：
MEM 故障 > EX 异常 > 中断 > 分支重定向。

中断 MTI/MSI/MEI（优先级 MEI>MSI>MTI）在 EX 级采样，仅当 EX 级含未退休
指令且流水线流动时触发。乘除运算及 load-use 互锁等待期间不采样中断；
电平中断保持 pending，待流水线恢复流动后再按精确边界接收。陷入时 mepc
记录本条指令 pc，handler 返回后重执行该指令。mtvec 支持
direct/vectored 两种模式；MRET 恢复 mstatus.MIE；WFI 为真睡眠
（mip&mie 非零即唤醒，不看 MIE）。FENCE/FENCE.I 实现为 NOP。

### 3.3 停机兼容机制（仿真测试设施）

mtvec 从未被配置（粘性 mtvec_valid=0）时，CPU 维持旧的停机行为与原因码
（ecall(1)/ebreak(2)/非法指令(3)/非对齐(4)/总线错误(5)/取指非对齐(6)），
使既有测试与 ACT/随机测试/跑分流程不受影响。软件一旦配置 mtvec，该行为
自动失效。这是为仿真测试设计的兼容设施，**不是** RISC-V 标准行为。

### 3.4 特权架构边界（明确未实现项）

- S/U 特权级及全部相关机制（medeleg/mideleg、stvec/scounteren、sret/uret、
  U/S 态 ecall 原因码 8/9 等）；
- 取指访问错误异常（cause 1）：取指口无越界检测，pc 越出 RAM 译码窗口时
  静默回绕而非陷入（已知限制；数据口访存越界已有 cause 5/7 覆盖）；
- Zicntr/Zihpm（cycle/time/instret CSR）与 mcountinhibit/mcounteren——
  周期计时由 MMIO 外设（0x1000_2000）承担；
- PMP、Sdtrig 触发器与调试模式、Rnmi（NMI）、hypervisor 扩展；
- mstatus 其余字段（MPRV/TW/TSR/TVM/FS/VS/XS 等均不存在）；
- PLIC/CLIC 中断控制器与可编程优先级——外部中断单线电平聚合进 MEIP，
  软件读外设状态判源，优先级固定 MEI>MSI>MTI；
- 中断嵌套无硬件双陷阱/优先级机制：handler 内二次陷入覆盖 mepc/mcause
  （规范允许，需软件自行保存）；mstatus 的 MIE/MPIE 机制支持软件保存 mepc
  后重开 MIE 实现嵌套，但此路径**无测试覆盖**。

验证缺口及替代覆盖：riscv-dv 框架内的中断异步注入未做（Sail 参考模型无法
接受外部中断），中断时序 fuzz 未做；中断路径正确性由自研定向场景
（test_irq/test_irq_ghost）与中断透明性随机化层（5.4 节）替代覆盖。

## 4. SoC 与外设

### 4.1 地址映射与中断聚合

| 地址段 | 模块 |
|---|---|
| 0x0000_0000 起 | RAM（FPGA 默认 64KiB；仿真可经参数放大，范围内回绕） |
| 0x1000_0000 | GPIO（32 位输入/输出，输入电平中断 IE） |
| 0x1000_1000 | UART（8N1，TX 4 字节 FIFO + RX，RX 有效电平中断） |
| 0x1000_2000 | 周期计数器（64 位自由运行，benchmark 计时用） |
| 0x1000_3000 | mtimer（CLINT 风格 mtime/mtimecmp，定时器中断） |
| 0x1000_4000 | uart_mon 总线监听采集外设（见 4.2） |

访问未映射地址触发总线错误异常（停机兼容模式下为停机原因码 5）。
中断聚合：mtimer → MTIP；UART RX、GPIO 输入、uart_mon FIFO 非空经或门
聚合进 MEIP（软件读各外设状态判源）；MSIP 由软件置位。外设寄存器接口
与核心数据口遵循同一 valid/ready 约定。

各外设寄存器总表（字访问，偏移为模块内地址；完整语义见对应
最终 Verilog 交付件头注释，本表与之一致）：

| 外设 | 寄存器（偏移） |
|---|---|
| GPIO | OUT RW（0x0）输出引脚；IN RO（0x4）输入引脚（同步后）；IE RW（0x8）输入中断使能，irq = \|(IN & IE) 电平 |
| UART | DATA（0x0）W 发字节（TX FIFO 满时 ready 拉低）/ R 收字节（读后清 rx_valid）；STATUS RO（0x4）bit0 tx_full、bit1 rx_valid；DIV RW（0x8）位周期（默认 16） |
| cyclectr | CYCLE_LO RO（0x0，读时锁存高半快照）；CYCLE_HI RO（0x4）——先 LO 后 HI 得一致 64 位值 |
| mtimer | MTIME_LO/HI RW（0x0/0x4）；MTIMECMP_LO/HI RW（0x8/0xC）；mtime ≥ mtimecmp 拉 MTIP，复位比较值全 1 |
| uart_mon | CTRL RW（0x0：bit0 en、bit1 irq_en、bit2 clear 自清零脉冲）；STATUS RO（0x4：bit0 非空、bit1 溢出锁存、[24:16] 条数）；TSTAMP RO（0x8，peek 头记录时间戳）；DATA RO（0xC，弹出头记录：bit7:0 数据、bit8 帧错误）；OVF_CNT RO（0x10）；BITDIV RW（0x14，位周期）；NOW RO（0x18，时间戳计数器快照） |

### 4.2 uart_mon 总线监听采集外设

应用环节的核心外设 uart_mon：只收不发，监听一路 8N1 串行波形，
每收到一个字节落一条记录进 FIFO。记录包含：数据字节、帧错误标志（停止位
采样为 0；奇偶错误位预留）、以及**接收完成时刻的 32 位时间戳**（外设内部
自由运行时钟计数）。

时间戳是本设计的核心决策：帧切分与响应时间计算全部由 CPU 依据硬件时间戳
之差完成。在采集 FIFO 与事件缓冲均未溢出、记录最终均被处理的前提下，字节
的接收时刻不依赖 CPU 何时取数，因此正常的调度延迟不会把完整消息拆错；
若繁忙到缓冲溢出，仍可能丢数据并由溢出计数和错误分类显式反映。

寄存器接口：TSTAMP（peek 头记录时间戳）与 DATA（读弹出头记录的数据与
标志）配对读取；FIFO 满时丢新字节、累计 OVF_CNT 并锁存溢出标志位——宁可
明确报溢出也不静默错位。BITDIV 寄存器可配位周期；FIFO 非空电平中断已并入
MEI 聚合（irq_en 已由固件启用：中断驱动取数，见 6.2 节）。

监听输入为 SoC 顶层端口 mon_rxd：仿真环境接内部发生器，上板时约束到扩展
引脚（经 RS-485 收发模块），产品 RTL 中无任何仿真专用逻辑。

### 5.3 同步陷阱随机化（randtrap）

验证目标：同步异常陷入路径的 mcause/mepc/mtval 现场正确性。随机程序中注入
陷阱片段（ecall/ebreak/非法指令编码池/非对齐 load-store），程序头部初始化
mtvec/mscratch，自带固定最小 handler——把 mcause/mepc/mtval/mstatus 转储到
签名区内日志、mepc+=4 跳过故障指令、mret 续行。Sail 黄金参考对同一 ELF
逐条执行同样的陷入与 handler，期望值完全由黄金参考产生，无任何手工推演的
拍级行为。

设计要点：

- 注入片段只覆写两个"注入寄存器"（避开 pygen 保留集后动态选定并补入
  保留集），不扰动程序原有状态与地址；handler 保存/恢复所用寄存器，
  净效果零扰动；
- 非法指令编码池经 Sail 探针逐条验证双方一致判非法（全 1、sret/dret 字段
  变体、写 satp、读 cycle、保留操作码 0101011），字段随机化只动双方译码
  均忽略的位；
- 注入点优先避开分支前跳跳过区间（实测该区间占主程序约 80%，不加规避时
  触发率仅 2/10）；
- handler 有日志溢出守卫：计划外重复触发（如注入落入回边）写 tohost=3
  硬失败，不会静默出错；
- 不覆盖中断（异步，Sail 无法注入）、WFI、vectored 偏移——由既有定向
  测试兜底。

### 5.4 中断透明性随机化（randirq）

验证目标：中断路径（MTI/MSI/MEI 陷入、精确边界、现场恢复）的随机化覆盖。
核心原理：**精确且透明的中断，打了和没打，程序最终架构状态必须逐位相同**。
因此期望值就是无注入基线的签名，与中断落在流水线哪个拍无关，零手工推演。

结构：常规随机程序（不含 CSR/陷阱，与中断正交）+ 固定前导（mtvec/mscratch/
mie/MIE/MSIP 初始化）+ 固定透明 handler（交换保存所用寄存器、陷入计数、
按 mcause 撤销中断源、mret 重执行被打断的指令）。handler 不知道打断了哪条
指令，其正确性由签名比对反向监督。

实现要点：

- 双 ELF 设计：Sail 版仅使能 MSIE（探针确认 Sail 的 CLINT 在 MTIE+MIE 下会
  自发拉起 MTIP，不能进基线；且 Sail 不响应 MSIP 软件写），RTL 版中断全
  使能；两版仅差前导一个立即数，地址布局一致；
- tb 注入引擎按周期计划注入：MTI 为层级沉积 poke mtimecmp（一次性语义，
  handler 经总线写全 1 撤销）；MEI 为按计划驱动 UART RX 线发字节
  （字节自撤销语义干净）。GPIO 电平注入未采用——电平撤销时机依赖拍级
  假设，与"零拍级推演"原则冲突，GPIO 中断路径由定向测试覆盖；
- 注入计划两轮生成：先无注入跑一遍实测总周期数 T，再按种子在窗口内
  均匀分桶随机布点（间隔不小于 500 拍，保证 UART 帧不重叠），注入次数
  随程序长短自适应；
- 判定链：Sail 签名 == RTL 无注入签名 == RTL 注入签名，且 handler 陷入
  计数 == 前导 MSI 1 次 + 计划注入条数（不等即 FAIL，防止"中断根本没
  发生"的假通过）。

### 5.5 随机化层的实战成果

randtrap 与 randirq 两层上线各检出并修复一个真实 RTL bug：

- MEM 级访存故障在乘除停顿期间被吞掉（停顿冻结逻辑漏了 MEM 级故障路径）；
- 中断采样到分支重定向产生的幽灵气泡时 mepc 记录错误（附定向回归测试
  test_irq_ghost）。

### 5.6 应用 demo 层

`make demo` 把应用数据通路整体跑通并覆盖全部诊断分支：tb 侧仿真总线
发生器按脚本发出 Modbus 波形 → uart_mon 采集 → 应用固件解析 → UART
输出诊断结果。场景集由 gen_script.py --scenario 参数化生成：

- 正常问答（基线，响应时间与理论推算逐拍一致）；
- 六类故障/边界：坏 CRC 回复、截断帧、异常回复（fc|0x80）、未支持
  功能码、无回复超时、广播请求；
- 多设备分账（multidev：4 台从站共线，画像逐台独立累计）；
- 三类跨帧模式诊断：链路干扰突发 interference、重试风暴 retrystorm、
  设备离线/恢复 offline；
- 长帧两态（自动波特率不误触发回归）：合法长帧 longframe（65 字节
  合法回复）、单个长坏帧 longbad（仅 1 个无效帧）；
- 波特率误配自恢复双路径：baudscan（主判据）/ baudbail（兜底判据）——
  总线以候选表内的非默认位速率发流量，固件按默认 32 开局 → 误配乱报 →
  自动扫描锁定 → 统计清零后诊断恢复；
- 命令接口场景×2（连续运行形态）：基本命令（stat/dev/clear/timeout/
  bitdiv/perf/help 与非法命令）、故障日志/告警命令（offline 场景流量
  + log/logclear/alarm，事件时间戳逐拍确定）。

判定链双重：固件自检与场景无关的不变式（帧分类完备、无溢出、
无帧错误）后经 GPIO 魔数报码（中断驱动固件配置了 mtvec，ecall/ebreak
走标准陷入而不再停机；tb +GPIOEND 以魔数写入为结束信号并核对其值），
同时 UART 输出经
+UARTLOG 落盘与 scripts/demo/golden/ 逐场景文本 diff（仿真输出逐拍确定，
golden 经人工核对后入库）；tb 另核「脚本必须全部发完」防止激励被截断
的假通过。发生器 CRC 由脚本独立计算，与固件实现交叉验证，并经 CRC
标准目录已知答案向量（"123456789" → 0x4B37）核对。

真实波特率量级复验（`make demo9600`，上板前验证补强不作门禁）：全部 15
个总线场景在 9600 波特量级（50 MHz → bitdiv=5208，一字符 57,288 clk）
复跑——位速率三处一致机制同 stress（+MONBITDIV / -DMON_BITDIV_CFG /
--bitdiv），候选表用默认 50 MHz 真实表，baudscan/baudbail 固件从 2604
（19200 波特）开局制造误配。结果：15 场景全部 RESULT: PASS；13 个静态
场景 STAT 分类计数与 bitdiv=32 golden 逐项一致，响应时间随位速率精确
缩放（1728 → 281,232 clk，恰为 5208/32 倍）；两个自动波特率场景的判据
指纹在真实量级下保持（baudscan 主判据：触发前有 crc_err 垃圾帧与干扰
诊断留痕；baudbail 兜底：触发前无 FRAME 行），均锁定 5208。整轮实测
合计 132,290,260 仿真周期（15 场景日志求和；walltime 约 85 秒），
单场景最大为 baudbail 40M 周期。结论：切帧/超时/
收敛/自动波特率的长时间窗行为与位速率量级无关，关闭 deploy.md 2.2 的
真实波特率缺口（32 位时间戳绕回不在其列：全部时序判断为 32 位减法判
差，差值远小于 2^31，绕回安全是设计性质而非实测项）。

压力测量（`make stress`，评估性质不作门禁）：stress 场景 N 对请求-回复
背靠背，扫「位速率 × 帧间隔」二维梯子找 uart_mon FIFO 溢出临界点——
STRESS_BITDIVS 扫位周期（越小总线越快），STRESS_CHARS 扫帧间间隔
（字符时间）。三处位速率由 Makefile 同一变量驱动保证一致：发生器
+MONBITDIV（mbus_gen 运行期覆盖）、固件 -DMON_BITDIV_CFG（en=0 时写
BITDIV 寄存器，切帧/超时阈值按读回值换算）、脚本 --bitdiv（请求-回复
延迟按字符时间换算）。OVF_CNT 与诊断分类如实上报。实测数据见 7 节。

### 5.7 pygen 适配的已知限制

- 上游 master 的 gen_callstack 有 bug（callstack_gen 未初始化），固定
  --num_of_sub_program=0 绕开，暂无子程序调用覆盖；
- 上游 rv32m_instr.py 把 REMU 误分类为 LOAD（会漏抽且可能混入访存定向流），
  已在适配层修正为 ARITHMETIC，未改外部组件源码；
- instr_cnt 是主程序规模上限（实际在 [10, instr_cnt] 随机），pygen 生成较慢
  （万条约 12 秒/种子，靠多核并行摊销）；
- Sail 按 Linux 启动协议把 a1 初始化为 DTB 地址，因此生成程序必须初始化
  全部 32 个寄存器（上游 init_gpr 会跳过 sp/tp，已在子类中覆盖）；
- 常规随机程序不含 CSR/陷阱/非对齐访存——同步陷阱由 randtrap 承担，
  中断/WFI 等异步路径由 randirq 与定向测试覆盖。

外部组件版本固定（riscv-arch-test、coremark、sail、riscv-dv、riscv-tests
及 ACT 框架工具链），清单维护在 AGENTS.md「新机器环境搭建」节；更换版本
须连同测试结果一起评估后再提交。

## 6. 应用设计：工业串行通信分析

### 6.1 模块边界（核心设计约束）

应用按"demo 与上板共用"和"仅仿真环境"严格分层：

| 产品侧（上板原样保留） | 仿真环境侧（上板后被真实总线替换） |
|---|---|
| uart_mon 采集外设（4.2 节） | mbus_gen 总线发生器（tb/，脚本 ROM 逐字节发 8N1 波形，帧间间隔与请求-响应延迟编在脚本里，改场景只改脚本不改 RTL） |
| 应用固件 sw/app/（6.2 节） | gen_script.py 场景生成（CRC 独立计算） |
| CPU/存储器/基础外设（不变） | tb_soc 的 +MONSCRIPT 激励设施 |

监听输入经 SoC 顶层端口 mon_rxd 进入：仿真时 tb 把发生器输出连到该端口，
上板时该端口约束到扩展引脚。中间没有任何仿真专用逻辑混进产品 RTL——
发生器发出的每一个比特都走与真实总线完全相同的采集路径。

### 6.2 固件分层

固件严格分为取数层与处理层：

- 处理层（proto.c）：协议解析核心，不接触任何 MMIO。输入是"字节+时间戳"
  记录，完成按空闲间隔切帧、Modbus CRC16 校验、FC03 请求/回复解析、
  异常回复识别（fc|0x80）、请求-回复配对与响应时间统计、待回复超时
  诊断（口径：阈值内未观察到有效回复，只陈述观察不归因设备故障；判定
  为双路径——proto_tick 墙钟 + 新请求覆盖补判，见 6.3 要点 4）；
  跨帧模式诊断（CRC 错误突发判链路干扰、同一请求连续无应答重发判重
  试风暴、已建立应答记录的设备超时判离线/再应答报恢复，口径见 6.4）；
  设备画像：按从站地址分账（请求/响应/异常回复/超时计数 + 响应时间
  分布样本数/最近/最小/最大），8 槽按首次出现顺序分配，表满新地址
  计 DEVS ovf 不静默；入账规则见 6.4；
  输出经 app_put_* 钩子。记录由谁喂入对解析逻辑不可见——轮询升级为
  中断驱动、handler 直喂升级为事件缓冲主循环喂入，两次取数架构调整
  本层与 RTL 均零改动（实测验证：升级后 demo golden 逐字节不变）；
- 取数层（main.c）：事件缓冲架构——报告打印已移出中断关键路径
  （handler 内同步打印曾使处理速率 551 clk/字节低于总线速率 352
  clk/字节，密集流量期单次 drain 长达 41k clk，MTI 节拍被饿死）。
  MEI 电平聚合——uart_mon FIFO 非空则 handler 只把记录搬进事件环形
  缓冲（128 条，满则丢计 ev_ovf 不静默），结果 UART RX 字节入命令
  缓冲（连续形态）；MTI handler 只重排下一拍并置节拍标志；主循环
  WFI 唤醒后排空事件缓冲喂处理层、队列追平（缓冲空 + FIFO 空）时
  执行 proto_tick、排空命令缓冲——解析与报告打印全在主循环上下文，
  中断仍可持续取数；缓冲未溢出时不会因打印阻塞丢失字节，缓冲满则按
  前述 ev_ovf 显式计数。proto_tick 的「静默超阈」条件保证
  传输中的帧不被节拍误切（见 6.3）；睡眠前关中断复检防丢唤醒（WFI
  有 pending 即唤醒，不看 MIE）；总线空闲时 CPU 零算力消耗；结果经
  UART 打印。
- 自动波特率（取数层职责，免配置接入与误配自恢复）：不做开机常开
  扫描（总线空闲时无流量可锁，且开局扫描会吃掉首段流量），而是后台
  误配检测，判据两级：主判据为连续无效帧（关闭时判 crc_err/len_err）
  ≥2 且自上一个 CRC 有效帧以来喂入字节 ≥64，有效帧关闭即清零重计——
  无效帧按关闭计而非按字节计，≥64 字节的合法长帧（如 FC03 读 30 个
  寄存器的 65 字节回复，longframe 场景回归）在传输途中不触发，单个
  被干扰的长坏帧（仅 1 个无效帧，longbad 场景回归）也不触发；兜底为
  累计字节 ≥512（2×协议最长帧）无条件触发，覆盖「位周期偏快、垃圾
  连绵且间隔始终低于切帧阈值、永不收帧」的方向（该形态下无效帧计数
  不增长）。两路径各有 demo 回归且指纹相异：baudbail（兜底）在误配+
  背靠背无间隔流量下扫描启动前无任何 FRAME 行；baudscan（主判据）
  触发前有若干 crc_err 垃圾帧与干扰诊断留痕（条数随误配比率漂移，
  不绑定具体数字）。字节阈值保留的意义：误配方向不同垃圾的成帧形态
  不同（过快→连绵超长帧、过慢→碎帧），字节数对两种形态都敏感。
  误配检测状态（快照基准）随 clear 命令同步重置，避免计数器清零后
  基准陈旧导致减法下溢误触发。
  扫描为候选位周期表轮询：en=0 窗口写 uart_mon BITDIV、clear、重新
  使能，开 48 字符观察窗，窗内 CRC 有效帧 ≥2 即锁定（CRC 复用 proto
  层同一实现导出，避免两处漂移）；锁不上换下一候选，整表循环，总线
  空闲时保持扫描等流量。锁定后按新位周期重算切帧/超时阈值与节拍并
  proto_init 清零重计——误配期间的垃圾统计不可信，不入账。纯固件
  实现（BITDIV 运行期可写），RTL 零改动；扫描期字节不喂 proto，
  MTI 节拍仅作观察窗推进的唤醒源。候选表按 MON_FCLK 从标准波特率集
  （115200~9600）自动生成：连续运行形态默认 50 MHz，得 {434, 868,
  1302, 2604, 5208} clk/位 ≙ {115200, 57600, 38400, 19200, 9600} 波特，
  上板只需按实际时钟覆盖 MON_FCLK；仿真自检形态用缩小版
  MON_FCLK=500000（{4, 8, 13, 26, 52}，baudscan/baudbail 以表内 52
  制造误配），同一条生成代码路径。
- 故障事件日志与 GPIO 告警：proto 层诊断上报点（坏帧/超时/四类 DIAG
  事件）经 app_log_event 钩子同步抛事件（proto 层保持不碰 MMIO），
  应用侧实现为 64 条环形事件日志（时间戳 + 类型 + 地址 + 辅助值，满
  则覆盖最旧且 drop 计数可查不静默），连续形态经 log 命令导出、
  logclear 清空；故障类事件（超时/链路干扰/重试风暴/设备离线）同时
  锁存 GPIO 告警位（gpio_out bit16，上板接 LED/蜂鸣器），告警口径
  见 6.4。bit16 与 demo 魔数报码（低 16 位）不冲突：tb +GPIOEND 只
  检测低半字，固件收尾写全字魔数会同时清掉告警位。

编译宏 DEMO_MODE 分两种形态（同一套 proto 解析逻辑）：仿真自检形态
（时间窗收敛 + 自检报码，make demo 用）与上板连续运行形态（永不退出，
结果 UART 下行整行命令：stat 查统计 / dev 查设备画像 / clear 清统计 /
timeout 查询或设置超时阈值 / bitdiv 查位周期配置 / perf 查性能计数 /
log 导出故障事件日志 / logclear 清日志 / alarm 查询或撤销 GPIO 告警 /
help）。命令接口在仿真中经 tb_soc 的
+RXFILE 注入设施完整验证（命令脚本与总线脚本格式一致，注入起点等
mbus_gen 发完后开始，与场景时序解耦）。

### 6.3 demo 场景与检出的设计要点

场景集完整清单见 5.6，诊断分类与场景设计逐条一致；正常场景
响应时间实测 1728 个时钟周期，与按脚本参数的理论推算逐拍一致。

demo 与压力测试过程检出并固化了四个真实设计要点：

1. **采集就绪先于总线流量**：发生器开场空闲必须留足固件启动与采集使能
   时间，否则使能前的流量被错过。对应上板后的真实约束：分析仪先就绪，
   再接总线。
2. **墙钟切帧的前提**：按"当前时刻距最后字节超过阈值"收尾帧，只能在
   CPU 已追平全部待处理队列（事件缓冲空且硬件 FIFO 空）时进行；否则打印
   阻塞期间到达的字节还躺在队列里，会被墙钟错切。硬件时间戳记录真实接收
   时刻，但只有先处理完这些已到达记录，才能安全使用当前墙钟判断静默。
3. **FIFO 空 ≠ 线上无字节在传**：回复帧传输期间（背靠背字节远慢于固件
   取数）FIFO 会暂时为空，墙钟操作（超时判定、demo 收敛）若只看 FIFO
   空就会误动——超时判定曾因此对传输中的回复误报，收敛判定曾因此提前
   停机。固化规则：一切墙钟判定须同时满足「事件缓冲空」「硬件 FIFO 空」
   与「总线静默超阈」三个条件；前两项保证无积压记录，第三项排除线上仍有
   字节正在传输但尚未形成新记录的情况。
4. **墙钟判定不能只有 tick 一条路径**：取数积压会把时间上分离的
   总线事件压成处理上连续的事件——新请求可能在两次 tick 之间覆盖
   挂起槽位，旧请求的超时判定机会被压没（原 handler 内打印形态实测
   7 帧背靠背即可形成单次 41k clk 的连续 drain，multidev 场景检出；
   事件缓冲形态下主循环打印阻塞同样造成缓冲积压与节拍顺延）。固化
   规则：超时判定除 proto_tick 墙钟路径外，须有事件驱动兜底——新请求
   覆盖挂起前，先用硬件时间戳补判旧挂起是否已超阈值。

### 6.4 已知边界（口径声明，非 bug）

以下行为边界经复查确认，真实 Modbus 流量不触发或属协议固有限制，
报告引用时按此口径：

- **单挂起槽位**：主站不等超时就发下一请求时，新请求覆盖旧挂起；
  覆盖时若旧挂起已超阈值则先补报超时（事件驱动兜底，见 6.3 要点 4），
  未超阈值被覆盖的旧请求超时不再计（标准 Modbus 主站一问一答，不触发）
- **画像入账规则**：仅 CRC 校验通过且可解析的 FC03 帧按地址入账；
  crc_err/len_err 帧的地址域不可信、unsupported 帧方向未知，均只计
  总线级不归因设备；广播（addr=0）不建账——请求/正常回复/异常回复
  三分支一致（真实 Modbus 广播无回复，addr=0 的回复只可能是伪造或
  损坏流量；broadcast 场景附伪造 addr=0 回复锁定此口径：全局统计
  如实计数，画像不出现 addr=00）；
  8 槽按地址首次出现顺序分配，表满时建账失败计 DEVS ovf（按失败次数，
  同一新地址的请求与回复各计一次——表满无处记录哪些地址溢出过）
- **同长帧方向歧义**：FC03 请求定长 8 字节，与 byte count 为奇数
  （非法值）的回复同长，固件优先按请求解析；合法回复字节数必为偶数，
  真实流量无此形态
- **帧间隔前提**：请求-回复间隔 < t3.5 的违规总线会并帧（判 crc_err
  + 超时）——被测总线须符合 RTU 帧间隔，这是此类监听分析仪的固有
  能力边界
- **广播口径**：广播请求（addr=0）如实打印但不挂起待回复、不报超时
  （广播本就不期待回复）
- **命令接口节奏**：结果 UART 的 RX 为单字节保持，上一条命令响应打印
  完成前发下一条命令会丢字节；人手敲命令无风险，PC 自动化须等响应
  返回再发下一条
- **跨帧模式诊断口径**（DIAG 行，阈值均为设计常数，proto.h 文件头同
  步记录）：
  - 链路干扰：连续 3 帧 CRC 错误才上报一次（单帧抖动属偶发误码，不
    上报；burst 扩大不重复报）；CRC 通过的帧清零计数；len_err 帧长
    度域不可信无法验证，不计入也不打断
  - 重试风暴：与上一请求签名全同（地址+起始+数量）且其间无有效应
    答的连续重发达 3 次才上报一次（episode 去重）；获有效应答或请
    求变更即复位——正常轮询同寄存器每次都获应答，不触发
  - 设备离线/恢复：仅对已建立应答记录（曾正常或异常回复）的设备，
    一次超时即报离线；再次应答报恢复并复位，之后可再次触发。从未
    应答过的设备超时只报 TIMEOUT 不报离线（它可能根本不在线上）
- **故障事件日志与告警口径**（实现见 6.2）：
  - 事件源：crc_err/len_err 帧、超时、四类 DIAG 事件（干扰/重试风暴/
    离线/恢复），与 UART 诊断输出同源同刻；日志是环形覆盖结构，导出
    行的绝对序号与 drop 计数使覆盖可察觉，clear 清统计不清日志
   （追溯优先），logclear 才清空
  - 告警锁存：超时/链路干扰/重试风暴/设备离线置位 gpio_out bit16；
    单帧 crc_err/len_err 不置位（偶发误码不告警，突发由干扰事件覆盖）；
    设备恢复不自动撤告警（其他故障可能仍在）；撤销只能经 clear（连
    同统计复位诊断面）或 alarm off 命令——告警是给人看的锁存信号，
    不随总线状态自动起落
- **自动波特率口径**（实现见 6.2）：
  - 触发与锁定：连续无效帧 ≥2 且自上一 CRC 有效帧以来累计 ≥64 字节
    判误配（≥64 字节的合法长帧与单个长坏帧均不触发）；兜底为累计
    ≥512 字节（2×协议最长帧）无有效帧无条件触发，覆盖垃圾连绵永不
    收帧的方向。候选观察窗 48 字符（字符时间，随候选位周期换算）
    内有效帧 ≥2 锁定。触发阈值是设计常数，对「正确速率下持续全损」
    的真实强干扰同样会触发重扫描——扫描会在干扰结束后重新锁定原
    速率，行为等价于自愈，视为可接受口径
  - 不误伤既有场景的论证：demo 最长连续无效流量仅 24 字节
    （interference 3 帧），字节阈值 64 裕量充足；无效帧数 ≥2 的
    条件进一步挡住了单帧长垃圾的误触发
  - 误配期间的症状本身会留痕：垃圾帧按 crc_err/len_err 如实上报，
    连续 CRC 错误还可能触发一次 link-interference 误报——分析仪在
    锁定前无法区分误配与干扰，属固有限制；锁定时 proto_init 清零，
    乱报不进入统计与画像
  - 锁定瞬间可能落在某对问答中间：该对的请求已在扫描窗内消耗，
    锁定后先看到一条无配对的孤儿回复（无 resp= 字段），属正常捕获
    而非丢失
  - 锁定后超时阈值按新位周期重算（16 字符），运行期 timeout 命令的
    自定义值随之失效（重新设置即可）；总线空闲时扫描不收敛、持续
    轮候选表等流量，命令接口保持可用

- 最终 PDS 时序优化版：同一工作量 3,450,027 周期，较前一版增加
  217,518 周期（约 6.73%）。最终版除 load-use 互锁外的保留改动不增加
  正常执行拍数，因此该差异主要反映取消 load 数据 MEM→EX 组合前递的代价。

周期增加不等于实际任务一定变慢，性能取舍须同时考察实现频率：
`任务耗时 = 执行周期数 / 实际时钟频率`。PDS 优化以该关系判断是否保留
会增加等待拍的方案；99.0589 MHz 为裸 SoC 报告估计，完整应用实际运行
点为 80 MHz，二者不能混作同一 CoreMark 实跑成绩。

### 7.1 应用层性能（总线监听，与 CoreMark 基线分开报告）

以下数据采集自 PDS 时序重构前的事件缓冲固件/处理器组合，用于说明应用的
主要瓶颈和缓冲架构收益，不作为最终优化版的精确吞吐复测。最终版的协议
处理、缓冲深度和报告策略未变；load-use 互锁可能改变部分 CPU 周期，相关
周期数据未逐项复测。在激励相同且采集 FIFO、事件缓冲均未溢出的回归条件下，
硬件时间戳决定的帧边界、响应时间和诊断分类不随这项前递改动改变；压力
临界点附近则必须重新检查溢出，不能套用这一结论。

测量口径：cyclectr 外设在固件取数循环内计时；"帧处理"指帧关闭那次调用
（切帧+CRC+解析+报告打印），UART 打印阻塞单独累计；仿真环境 BITDIV=32
（位周期 32 clk）、结果 UART DIV=16（176 clk/字符）。

- 采集服务开销：handler 弹读入队为数十拍量级（不单独计时）；主循环
  纯喂入+解析 ≈19 clk/字节（(feed_cyc−frame_cyc)/bytes，stress 实测
  9,618/510）
- 每帧处理 ≈5,517 clk/帧（330,995/60，含约 30 字符报告打印——uart_wait
  292,038 clk 占 88%），无溢出配置下最差帧 6,592 clk；
  **纯解析计算只占几百 clk，瓶颈是报告打印**（与取数架构无关）
- 诊断延迟构成：切帧等待 t3.5 = 1,232 clk（设计常数）+ 节拍量化 + 帧处理。
  无打印阻塞且队列正常追平时，节拍量化额外延迟 < 半切帧阈值；主循环打印
  阻塞期间相应顺延，事件缓冲提供兜底，未溢出时不会因打印阻塞丢失字节
- 持续吞吐临界点（`make stress` 二维梯子，30 对请求-回复背靠背，事件
  缓冲形态实测）：帧间间隔 6 字符时 bitdiv=32 可持续（50 MHz 时 ≈1.56
  Mbaud）；间隔压到协议下限附近（4 字符，切帧阈值 3.5）时可持续最高
  速率 ≈40 clk/位（≈1.25 Mbaud），36 clk/位起溢出；bitdiv=24 可持续到
  12 字符间隔。溢出面已从 uart_mon FIFO（64 深）转移到事件缓冲（128
  深）：全梯子 MON OVF_CNT 保持 0，溢出以 ev_ovf 计数（36 clk/位 @ 4
  字符 17 条、32 @ 5 34 条、32 @ 4 59 条、24 @ 10 17 条），丢失字节由
  crc_err/len_err 如实归类、系统不崩不离谱
- 事件缓冲形态对比（handler 内打印 → 主循环打印，同一梯子复测）：临界
  线全面外推——4 字符间隔可持续速率 44→40 clk/位，bitdiv=32 可持续间
  隔 8→6 字符，bitdiv=24 由 12 字符间隔即溢出转为可持续；旧三个近界溢
  出点全部转干净（32 @ 6 字符 OVF 12→0、40 @ 4 5→0、24 @ 12 3→0）。
  根因：handler 不再被报告打印阻塞（百拍级返回），MTI 节拍不再被饿死，
  缓冲总量 64→192 字节。剩余瓶颈仍是逐帧报告打印（≈5.5k clk/帧，纯解
  析仅占约一成）——要再提上限须精简逐帧报告，属应用策略而非取数架构
  问题
- 测量口径边界：帧间间隔 ≥16 字符时与默认超时阈值（16 字符）相等，
  会在响应首字节接收完成前报超时（「阈值内未观察到有效回复」字面
  成立，监听者只能在字节收完后才看得到它），属测量配置边界非缺陷
- 上板意义：真实总线 9600 波特下一字符 ≈ 1 ms，相对仿真速率（50 MHz 时
  一字符 352 clk ≈ 7 µs）裕量约两个数量级，当前中断驱动取数形态足以应对；
  若关闭逐帧报告打印，吞吐上限还可大幅提升（计算开销仅占总帧处理约 10%）

### 7.2 紫光 PDS 时序分析与最终实现

最终时序优化以**紫光 PDS 的实际综合和布局布线结果**为依据。实验器件为
Logos PGL50H-6 FBG484，工具为 PDS 2022.2 SP6.4，并检查不同工艺角下的
建立与保持时间。早期 yosys 的 LUT 级数只用于快速观察路径构成，不能换算
为纳秒，也不作为本版最终频率或资源结论。

优化过程不是一次性重写，而是反复执行“PDS 报告定位慢路径 → 分析起点、
终点及逻辑/连线延迟 → 修改 RTL 或实现策略 → 重新实现并复测”的闭环：

1. PDS 首先暴露数据存储器读出后经前递、分支比较和改向控制到取指地址的
   长路径，因此取消 load 数据的 MEM→EX 组合前递，改为 load-use 互锁。
2. 慢路径起点转向寄存器堆后，检查资源报告发现行为改写仍被映射为 DRM，
   遂显式实例化触发器，落实预期的寄存器堆物理结构。
3. 针对写回编号、MEM 编号和写控制资格引发的慢路径，将 WB 匹配及完整
   MEM 前递资格随对应流水数据提前寄存。
4. 针对 MEM 异常绕经 load 等待和年轻级控制的路径，重构总陷入请求；针对
   清空控制的高扇出，分离宽数据与有效/控制状态的更新。
5. 针对目标加法与比较串联、vectored 中断入口加法等路径，采用 2.5 节的
   目标与候选值预计算以及中断入口缓存。
6. RTL 结构稳定后固定源码、程序映像、器件和约束，继续通过 PDS 布局、
   布线及种子对照改善同一结构的物理实现。

各阶段 PDS 实现记录如下。约 77～89 MHz 是不同修改阶段的频率，不是在
同一最终结构上并列可选的工作点；后期物理对照统一使用 11.50 ns 约束。

| 阶段或修改 | PDS 结果/现象 | 设计决策 |
|---|---:|---|
| 行为描述寄存器堆 | 约 77 MHz，仍映射为 DRM | 硬件意图未落实，继续修改映射 |
| 显式触发器寄存器堆 | 约 80 MHz | 采用，寄存器堆输出路径改善 |
| WB 前递匹配提前 | 约 83 MHz | 采用，写回编号路径退出主要慢路径 |
| MEM 异常控制重构 | 约 84.6 MHz | 采用，异常地址链不再占多数慢路径 |
| 宽数据与清空控制解耦 | 约 89 MHz | 采用，继续转向完整前递资格与物理连线 |
| 完整 MEM 前递资格提前等最终结构 | 94.1620 MHz，WNS +0.880 ns | 作为后续物理优化的统一 RTL 起点 |

固定最终 RTL 后，先比较 normal/performance 两类模式及种子 0～3，再在
有效候选上调整详细布局和关键路径布线。详细布局由 Bump 改为 Swap，随后
采用 20 条路径、1.6 ns 筛选参数进行优先布线迭代，结果如下：

| 同一最终 RTL 的实现 | 报告 Fmax | 最差建立时间裕量 |
|---|---:|---:|
| 结构稳定后的裸 SoC 对照 | 94.1620 MHz | +0.880 ns |
| Swap 布局 | 96.3391 MHz | +1.120 ns |
| 优先布线中间结果 | 98.8142 MHz | +1.380 ns |
| 最终封存结果 | **99.0589 MHz** | **+1.405 ns** |

从对照到封存结果的约 5.20% 提升完全来自固定 RTL 后的物理实现。最终
慢角、快角保持时间裕量分别为 +0.038 ns、+0.030 ns；资源为 4230 LUT、
2904 FF、268 分布式 RAM、4 APM、64 DRM。完整布局布线数据库已封存，
并由该数据库重新生成报告复现 99.0589 MHz，说明结果不是一次不可追溯的
偶然实现。

最终最慢路径仍由 MEM 控制经前递、分支比较、改向/陷入汇总到指令 RAM
地址，数据通路合计 10.113 ns，其中逻辑 3.029 ns、连线 7.084 ns
（70.048%），仅末段取指地址到 RAM 就为 2.059 ns。另一条 IF/ID 地址经
BHT、译码改向、BTB 查询到预测命中寄存器的路径几乎同样慢：两者建立
裕量分别为 +1.405 ns 与 +1.409 ns，只差 0.004 ns，后者连线占比也达
66.080%。因此继续单点缩短算式会受到另一条路径限制，优化重点已由
逻辑级数转为公共控制和存储器连接的物理分布。

以下尝试经同样的 PDS 实现对照后未采用，不属于最终架构：

- 额外寄存分支纠正/陷入事件：阶段频率约提高 1.06%，任务周期却增加
  约 2.11%，换算任务耗时反而增加约 1.03%；
- 两候选预测地址并行查询：LUT 增约 6.93%、FF 增约 2.20%，同类布局下
  Fmax 从 96.3391 降至 90.2201 MHz；
- 比较器按 8/4 位分段、RAM 地址分两组/四组：完整实现均差于对照；
- 对 14 条取指地址统一限制最大扇出为 16：扇出确实下降，但 Fmax 从
  94.1620 降至 81.8934 MHz，说明驱动位置和连线分布比单纯扇出数字更关键。

这些负结果也是停止扩大修改的依据：当多条路径接近且连线延迟占主导时，
盲目复制逻辑、拆分表达式或增加流水拍未必获得端到端收益。

### 7.3 完整板级实现、资源与频率口径

裸 SoC 的频率估计与完整板级应用必须分开报告。前者用于比较处理器结构
和物理实现，后者还包含 PLL、实际引脚和应用接口，布局条件不同。

| 结果对象 | 目标周期 | 报告 Fmax | 建立时间裕量 | 结论 |
|---|---:|---:|---:|---|
| 裸 SoC 最佳实现 | 11.50 ns | 99.0589 MHz | +1.405 ns | 封存并复现 |
| 裸 SoC 100 MHz 目标试验 | 10.00 ns | 99.5322 MHz | −0.047 ns | 未满足 100 MHz，不宣称通过 |
| 完整应用 PLL 100 MHz 试验 | 10.00 ns | 94.5626 MHz | −0.575 ns | 未采用 |
| 完整应用 PLL 90 MHz 试验 | 约 11.1111 ns | 89.9838 MHz | −0.002 ns | 未采用 |
| 完整应用 PLL 80 MHz | 12.50 ns | **83.3820 MHz** | **+0.507 ns** | 实际上板运行点 |

完整应用由板载 50 MHz 晶振经 PLL 按 8/5 倍频产生 80 MHz CPU 时钟。
资源为 4224 LUT、2858 FF、268 分布式 RAM、4 APM、64 DRM、1 PLL 和
13 个 I/O。约束工作包括真实输入/派生时钟关系、引脚与电平、异步按键和
串口入口例外，以及 LED 和串口发送的输出传播预算；CPU 内部单拍路径仍
接受正常时序检查。

最终完整应用已完成真实 RS-485 正常通信、故障诊断和超过 10 分钟连续
运行，告警 LED 的置位与清除也经实物确认。报告引用时应写成“裸 SoC
最佳 PDS 报告 Fmax 99.0589 MHz，完整板级应用报告 Fmax 83.3820 MHz、
实际运行 80 MHz”，不能把裸 SoC 的估计值写成整机实际运行频率。

实现结果的可追溯性依赖完整资料共同保存：最终 Verilog、程序映像、约束、
实现策略与种子、布局布线数据库及对应时序报告。更换约束会改变 PDS 的
搜索方向，更紧的目标不保证得到更快结果，因此各组实现须独立保存，不能
只保留一个 RCF 文件或一张汇总表。
