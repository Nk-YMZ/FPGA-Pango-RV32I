# 处理器时序优化整理

供报告撰写与队内讨论使用。本文保留主要改动、路径证据、关键数据和取舍原因，队友可以按篇幅筛选。

## 一、优化目标与最终结果

我们最初设计五级流水线 RV32IM 处理器时，优先考虑减少程序执行周期，因此保留了较完整的数据前递、分支预测和较快的分支纠正机制。但这些机制互相连接后，也形成了较长的组合通路，限制了时钟频率。

后续优化的主线是：

```text
分离存储器读出与后续运算
    → 改变寄存器堆的实际映射
    → 提前保存前递选择条件
    → 缩短异常、清空与取指控制的串联
    → 固定结构，改善布局布线
```

我们同时比较频率、同一任务的执行周期和资源占用。对会增加等待拍的修改，判断依据是最终任务耗时：

```text
任务耗时 = 执行周期数 ÷ 实际时钟频率
```

实验采用 Logos PGL50H-6 FBG484 器件、PDS 2022.2 SP6.4 工具，并检查多角时序。主要结果如下。

| 结果对象 | 施加的时钟周期 | 报告 Fmax | 最差建立时间裕量 | 采用情况 |
|---|---:|---:|---:|---|
| 结构稳定后的裸 SoC 对照 | 11.50 ns | 94.1620 MHz | +0.880 ns | 后续物理优化的统一起点 |
| 同一结构的最佳物理实现 | 11.50 ns | 99.0589 MHz | +1.405 ns | 封存保留，重新出报告已复现 |
| 裸 SoC 的 100 MHz 目标试验 | 10.00 ns | 99.5322 MHz | −0.047 ns | 未满足 100 MHz 目标 |
| 完整板级监听应用 | 12.50 ns | 83.3820 MHz | +0.507 ns | 实际采用 PLL 80 MHz，已上板验证 |

其中，94.1620→99.0589 MHz 的改善来自固定 RTL 后的物理实现，提升约 **5.20%**。最终实现资源为 **4230 LUT、2904 FF、268 分布式 RAM、4 APM、64 DRM**，与该组对照保持一致。

早期约 77、80、83、84.6、89 MHz 是各阶段的实现记录，主要用于说明优化方向如何变化；后期布局布线对照统一采用 11.50 ns 约束。

## 二、先切开数据存储器到执行控制的长通路

### 1. 原来的问题

为了尽量减少 load 相关等待，原结构允许 MEM 阶段读出的数据直接前递到执行级。如果后一条指令利用这个数据判断分支，存储器读出后还要继续完成操作数选择、分支判断和下一取指地址生成。

关键通路为：

```text
数据存储器读出 → 操作数选择 → 分支判断
              → 改向控制 → 下一取指地址
```

这条通路的问题在于，存储器输出已经消耗了一段时间，后面仍接着较多判断。只改最后一个选择表达式，难以消除前面的连续依赖。

### 2. 我们改了什么

我们把 MEM 的完整写回数据与执行级前递数据分开：

| 项目 | 修改前 | 修改后 |
|---|---|---|
| MEM 向 EX 提供的数据 | 包括当拍读出的 load 数据 | 只包括已经寄存的非 load 结果，如 ALU 结果或 PC+4 |
| MEM 前递资格 | 写寄存器、目的编号有效且匹配 | 在原条件上排除 load |
| 紧邻 load 且依赖其结果的指令 | 尽量直接使用 MEM 读数 | 在 EX 等待，再从 WB 使用结果 |

执行操作数的数据源变化可以概括为：

```diff
- fwd1_mem ? exmem_fwd_data : ...
+ fwd1_mem ? exmem_exec_fwd_data : ...
```

相应的数据流变为：

```text
当前拍：数据存储器读出 → MEM/WB
下一拍：WB 前递 → 操作数选择 → 分支判断
```

### 3. 为什么接受这个取舍

这一修改会增加部分 load 相关指令的等待，单位频率下的 CoreMark 表现有所回退，与最初尽量压低周期数的目标存在取舍。但结合后续整体实现结果，时钟频率的提升幅度明显高于这部分程序效率损失，因此我们采用了这一方向。

这项修改之后，慢路径的主要起点转向寄存器堆输出。下一步因此转为检查寄存器堆究竟被综合成了什么硬件。

## 三、让寄存器堆真正采用触发器实现

### 1. 第一次改写没有落实原意图

寄存器堆只有 32×32 位。我们原本希望用独立寄存器保存各个字，再通过两个读选择树取数，避免块 RAM 输出延迟。

但第一次只调整行为描述后，综合报告仍显示寄存器堆使用 **1 个 DRM、0 个 FF**。虽然源码看起来像独立寄存器，工具依然识别成了存储器；当时频率约为 77 MHz。

### 2. 最终采用的实现

我们改为显式实例化 `GTP_DFF_E`：

- x1～x31 共 31×32＝992 位状态由触发器保存。
- x0 固定输出零，不分配同样的存储状态。
- 写入按目的编号产生各字的写使能。
- 两个异步读口共享这一份寄存器状态，各自通过选择树取数。

| 对比项 | 行为描述改写 | 显式触发器实现 |
|---|---|---|
| 实际存储映射 | 仍为 DRM | 触发器 |
| 读数路径 | 存储器输出后接前递控制 | 读选择树后接前递控制 |
| 阶段 Fmax | 约 77 MHz | 约 80 MHz |
| 后续主要限制 | 寄存器堆输出 | 写回编号与前递选择控制 |

这里有一个直接影响后续工作的结论：**修改是否有效，需要同时检查结构有没有实现，以及实现之后整体是否更快。** 第一次改写属于硬件意图没有落实，显式触发器则落实了意图，并取得了阶段改善。

## 四、把 WB 前递匹配提前计算

### 1. 原来的连续判断

原来执行级使用 WB 数据时，需要在当前拍比较写回目的编号与源寄存器编号。比较完成之后，再进行前递选择和分支判断。

```text
memwb_rd → 编号匹配 → 前递选择 → 分支比较
```

我们发现，这个匹配关系可以在 MEM/WB 更新之前准备，不必一直留到执行级当前拍才计算。

### 2. 具体调整

新增 `fwd1_wb_q`、`fwd2_wb_q` 两个标志，与 MEM/WB 同拍更新。执行级直接使用保存好的匹配结果。

对第一个源操作数，其核心关系为：

```verilog
wire [4:0] fwd1_next_rs = stall_young ? idex_rs1 : rs1_d;
wire fwd_next_write = exmem_ctrl[21] && !trap_mem &&
                      (exmem_rd != 5'd0);
// 在 !stall 时，与 MEM/WB 数据一起更新：
fwd1_wb_q <= fwd_next_write && (exmem_rd == fwd1_next_rs);
```

数据选择采用互斥条件，优先级保持为：

```text
MEM 前递 > WB 前递 > 已保存的原操作数
```

提前一拍的关键是让标志与数据始终对应，特别是暂停时不能错位。

| 情况 | 标志更新方式 |
|---|---|
| 正常推进 | 使用译码级的源编号，准备下一拍匹配 |
| 只有年轻级暂停 | 使用执行级保留的源编号 |
| 全局暂停 | 标志与相关流水数据一起保持 |
| load 等待 | 继续保留原操作数保存规则，避免丢失当时可用的 WB 数据 |

### 3. 结果与下一步

改后路径变为：

```text
fwd1_wb_q → 前递选择 → 分支比较
```

阶段 Fmax 从约 **80 MHz 提高到 83 MHz**，资源约增加 1%。原写回编号路径退出前 100 条慢路径。

新的前 100 条路径中，87 条从 MEM 地址寄存器出发，13 条来自译码。我们因此没有继续围绕 WB 编号做小修，而是转去检查异常控制。

## 五、缩短 MEM 异常返回总陷入控制的绕行

### 1. 从报告定位到控制依赖

一条详细路径从 `exmem_alu[30]` 出发，最终到 `mepc_r[4]` 的写使能。沿途发现，MEM 异常先改变 load 等待，再影响年轻级异常或中断判断，最后才返回总陷入控制 `trap_any`。

```text
访存地址 → MEM 异常 → load 等待释放
        → 年轻级异常或中断判断 → trap_any → CSR 写使能
```

该阶段最差路径的连线占比达到约 75.6%；其中 `trap_any` 扇出 111，一段连线延迟为 1.447 ns。除了条件层数，公共控制信号的分发也已经很重。

### 2. 我们如何改写

我们把“原始 load 等待”和“经过 MEM 异常取消后的等待”分开，并提前准备年轻级异常、中断候选。

随后让 MEM 异常直接进入总陷入表达式，避免绕过后级门控再回来。

| 修改对象 | 修改前 | 修改后 |
|---|---|---|
| load 等待 | 等待条件中直接混入 MEM 异常 | 先形成原始等待，再处理异常取消 |
| 年轻级请求 | 依赖前面已经门控的控制结果 | 候选条件尽量并行准备 |
| 总陷入控制 | 合并经过多层门控的请求 | MEM 异常直接进入 `trap_any` |
| 原因与现场地址 | 按既有异常、中断优先级选择 | 沿用原优先关系 |

改后的 MEM 异常主通路缩短为：

```text
访存地址 → MEM 异常 → trap_any → CSR 写使能
```

### 3. 结果

阶段 Fmax 从约 **83 MHz 提高到 84.6 MHz**，资源还出现下降。访存地址异常链不再占据多数慢路径，前递和取指控制重新成为重点。

这次修改调整的是判断条件之间的依赖关系，没有给异常处理再增加一个流水阶段。

## 六、把宽数据与清空控制分开

### 1. 原来的控制负担

IF/ID 中的 PC 和预测目标合计 64 位，原来和其他流水状态一起受清空控制。清空不仅决定指令是否有效，也参与这 64 位数据的更新条件。

我们检查后发现，判断走错路径的指令是否作废，主要依靠指令及有效标志；这两组宽数据不必继续承担同样的清空门控。

### 2. 具体修改

| 对象 | 修改前 | 修改后 |
|---|---|---|
| IF/ID 的 PC 和预测目标 | 暂停、清空共同控制更新 | 独立更新，只在暂停时保持 |
| 指令、有效位、预测标志 | 清空时作废 | 保留原处理 |
| PC 选择中的 ID 改向条件 | 使用经过门控的 `id_redirect` | 在对应选择分支使用原始 `id_redirect_req` |

最后一项能够去掉重复判断，是因为 PC 选择外层已经处理保持、陷入和 EX 纠正。清流水逻辑仍使用原来的改向控制，保持指令作废行为。

### 3. 结果

阶段 Fmax 从约 **84.6 MHz 提高到 89 MHz**，资源略有下降。

这一阶段的前 100 条慢路径中：

- 67 条到指令 RAM。
- 15 条到数据 RAM。
- 15 条到 CSR。

最差取指路径的连线占比约为 66.4%。优化重点开始从单一判断转为公共控制链及其物理连接。

## 七、提前保存完整的 MEM 前递选择资格

### 1. 只提前比较编号还不够

另一条慢路径从 `exmem_rd[0]` 出发，经操作数选择、比较、改向，最后到异常入口相关寄存器。

MEM 前递不只需要编号相等，还需要判断：

```text
是否写寄存器 + 是否为非 load + 是否为有效指令
             + 目的编号是否非零 + 源目的编号是否匹配
```

如果只保存编号匹配，其他资格仍在当前拍判断，前递选择前的串联就没有完全消除。

### 2. 我们最终前移了什么

新增 `fwd1_mem_q`、`fwd2_mem_q`，与 EX/MEM 同拍保存完整选择条件。

核心条件为：

```verilog
wire fwd_next_mem_write = idex_ctrl[21] && !idex_ctrl[18] &&
                         !exmem_bubble && (idex_rd != 5'd0);
// 在 !stall 时，与 EX/MEM 数据一起更新：
fwd1_mem_q <= fwd_next_mem_write && (idex_rd == fwd1_next_rs);
```

其中，`exmem_bubble` 与 EX/MEM 控制共用同一套气泡判断，包含乘除等待、load 相关等待、陷入和 WFI 请求等情况。源编号选择继续采用前面 WB 匹配中已经整理的正常推进及暂停规则。

路径变化为：

```text
改前：exmem_rd 与写控制 → 匹配、资格判断 → MEM 前递选择
改后：fwd1_mem_q / fwd2_mem_q → MEM 前递选择
```

### 3. 结果

这一项新增两个 FF，保留原有流水级数。结构稳定后的同源实现达到 **94.1620 MHz**，11.50 ns 约束下建立时间裕量为 **+0.880 ns**。

这成为后续布局布线试验的统一结构起点。后面的 99.0589 MHz 结果沿用这一结构，主要改善来自物理实现。

## 八、固定 RTL 后的布局布线策略

### 1. 先建立同条件对照

我们固定源码、程序映像、器件和 11.50 ns 约束，先比较：

```text
normal 模式：种子 0、1、2、3
performance 模式：种子 0、1、2、3
```

共八组。每组独立保存输出，记录最差建立时间裕量、慢快角保持时间裕量、Fmax 和资源，避免工程输出被覆盖后失去比较依据。

随后在有效候选上研究详细布局方式及关键路径优先布线。

### 2. 从 Bump 改为 Swap

详细布局由 Bump 改为 Swap 后，在同一结构上取得改善：

| 实现策略 | 报告 Fmax | 建立时间裕量 |
|---|---:|---:|
| 原对照 | 94.1620 MHz | +0.880 ns |
| Swap 布局 | 96.3391 MHz | +1.120 ns |

这一步约有 2.31% 的频率提升，说明当时结构仍有通过位置调整改善的空间。

### 3. 对最慢路径优先布线

我们继续采用 **20 条路径、1.6 ns 筛选参数**，先迭代 10 轮，再保留较好实现继续比较。

| 保留结果 | 报告 Fmax | 建立时间裕量 |
|---|---:|---:|
| Swap 布局对照 | 96.3391 MHz | +1.120 ns |
| 优先布线中间结果 | 98.8142 MHz | +1.380 ns |
| 最终封存结果 | 99.0589 MHz | +1.405 ns |

1.6 ns 是当次路径筛选参数；20 条是本次优先处理规模。这些参数来自本工程的试验结果，报告中可作为具体操作证据。

从原对照到最终结果，报告估计周期由约 **10.620 ns 降至 10.095 ns**，缩短约 **0.525 ns**；Fmax 提高约 **5.20%**。

这几组物理实现的资源都保持为 4230 LUT、2904 FF、268 分布式 RAM、4 APM、64 DRM。最终慢角、快角保持时间裕量分别为 **+0.038 ns、+0.030 ns**。

### 4. 如何保留这个结果

我们保留完整布局布线数据库，并从封存数据库重新生成时序报告，精确复现了 99.0589 MHz。

RCF 文件记录布线约束与优先级；实际采用哪些位置和线路，需要由完整实现数据库保存。因此，交接时应一并保留源码、程序映像、约束、实现设置、数据库和对应报告。

更换时钟约束后，工具会改变搜索方向，可能重新选择位置和线路。更紧的目标不一定得到更快实现，这也是我们固定 11.50 ns 做物理对照、独立保存各组结果的原因。

## 九、尝试过但没有采用的方向

### 1. 增加事件处理拍

我们尝试把分支纠正、陷入等事件额外寄存一拍，希望切开改向控制。

早期对照中：

| 指标 | 原结构 | 额外事件级 |
|---|---:|---:|
| 阶段 Fmax | 84.6 MHz | 85.5 MHz |
| 相同任务周期 | 3,450,027 | 3,522,746 |
| 按上述频率换算的任务耗时 | 约 40.780 ms | 约 41.202 ms |

频率只提高约 **1.06%**，任务周期却增加约 **2.11%**，换算耗时反而增加约 **1.03%**。

后续将这一思路与其他有效改动组合，在同样 11.50 ns、Swap 策略下，得到 **94.0822 MHz**，仍低于原结构的 **96.3391 MHz**。

因此，我们没有保留额外事件级。它说明切短组合通路的同时，还要考虑分支和陷入多等一拍对程序效率的影响。

### 2. 并行查询两个候选预测地址

尝试把“先选择地址、再查询预测表”改为“两个候选地址分别查询、最后选择结果”。

| 指标 | 参考结构 | 并行查询 |
|---|---:|---:|
| 综合 LUT | 4229 | 4522 |
| 综合 FF | 2904 | 2968 |
| 同类布局下 Fmax | 96.3391 MHz | 90.2201 MHz |

LUT 增加约 **6.93%**，FF 增加约 **2.20%**，时序反而退步。

可能原因包括输入分发负担增加、复制后的逻辑位置分散、末端选择变重。现有数据说明这次完整复制没有取得收益；若以后重做，更适合只针对明确的慢段缩小复制范围。

### 3. 拆分比较器与 RAM 地址网络

以下结构试验同样采用 11.50 ns、Swap 策略比较。

| 尝试 | 改动意图 | Fmax | 结果 |
|---|---|---:|---|
| 比较按 8 位分段 | 分段比较后合并，减少连续依赖 | 87.4202 MHz | 低于对照 |
| 比较按 4 位分段 | 进一步拆小局部比较 | 84.8608 MHz | 低于对照 |
| RAM 地址分成两组 | 调整驱动与负载的分布 | 90.5223 MHz | 低于对照 |
| RAM 地址分成四组 | 进一步分散地址驱动 | 86.8734 MHz | 建立时间裕量 −0.011 ns |

分段比较可能增加段间连接，也可能改变工具原本能够利用的比较、进位资源。RAM 分组则会改变驱动和负载的位置关系。它们在表达式上更分散，却没有在完整实现中胜出。

### 4. 整组取指地址限制扇出

我们还尝试对 14 条有效地址网络限制最大扇出为 16。约束确实生效：工具生成了额外驱动，关键网络扇出从 32 降到 16。

两组采用相同的 11.50 ns、performance、种子 0，关闭路径优先级迭代，并从源文件重新实现。

| 指标 | 原地址驱动 | 整组扇出限制 |
|---|---:|---:|
| Fmax | 94.1620 MHz | 81.8934 MHz |
| 建立时间裕量 | +0.880 ns | −0.711 ns |
| 综合 LUT | 4229 | 4255 |
| 综合 FF | 2904 | 2904 |

频率下降约 **13.03%**。复制后的末段地址线仍约 2.6 ns，前 100 条慢路径全部集中到了指令 RAM 地址。

这次试验说明，仅降低每个驱动的负载数量还不够。新驱动要放在哪里、输入控制如何送达、负载是否靠近，都可能影响最终结果。因此，我们停止整总线限制，后续只考虑有明确位置依据的局部调整。

## 十、最终关键路径与停止优化的依据

### 1. 最慢路径仍连接执行控制和取指地址

最终报告中的主路径为：

```text
exmem_ctrl[18] → MEM 前递数据 → rs1_e[2] → 大小比较
              → cti_mis_e → trap_any → PC 选择
              → imem_addr[4] → 指令 RAM 地址端
```

发射点为 `core_i/exmem_ctrl[18]`，终点为 `imem_i/mem_0/iGopDrm/ADA0[2]`。

| 路径项目 | 延迟 |
|---|---:|
| 数据通路合计 | 10.113 ns |
| 逻辑延迟 | 3.029 ns |
| 连线延迟 | 7.084 ns，占 70.048% |
| 其中末段取指地址到 RAM | 2.059 ns |

按通路顺序分段，可进一步看到时间花在哪里：

| 路径段 | 延迟 |
|---|---:|
| 发射与 MEM 控制 | 1.022 ns |
| MEM 数据到执行操作数 | 1.610 ns |
| 分支大小比较 | 1.813 ns |
| 改向判断到 `cti_mis_e` | 1.313 ns |
| 控制合并到 `trap_any` | 1.594 ns |
| PC 地址选择 | 0.702 ns |
| 取指地址到 RAM | 2.059 ns |

这条路径已经不再只是某个比较表达式太长。末段 RAM 连接占用明显，公共控制与前递数据的分布也在影响时序。

### 2. 另一类路径已经几乎同样慢

另一条接近的路径为：

```text
ifid_pc[4] → BHT 读取 → 译码重定向 → BTB 查询地址选择
           → BTB 标签读取与匹配 → if_pred_hit_q
```

| 路径 | 建立时间裕量 | 连线占比 |
|---|---:|---:|
| MEM 控制到指令 RAM 地址 | +1.405 ns | 70.048% |
| IF/ID 地址到预测命中寄存器 | +1.409 ns | 66.080% |

两条不同功能链的裕量仅差 **0.004 ns**。其中预测查询地址的一位扇出达到 131，一段分发连线为 0.816 ns，标签相关连线还有 1.134 ns 的延迟。

所以，即使只把最慢路径的一小段明显缩短，另一条预测路径也可能立即接替成为限制。后续需要同时关注两类路径及其公共部分。

### 3. 为什么在此阶段收手

我们停止扩大修改，主要有三个依据：

1. 两类不同路径已经非常接近，单点修改的全局收益开始受其他路径限制。
2. 连线延迟占比均超过 66%，增加逻辑、复制宽查询或统一限制扇出，已经出现多次实测退步。
3. 增加纠正拍会损失程序执行效率，而现有试验没有带来足以补偿的提频。

因此，我们保留已经复现的 **99.0589 MHz** 实现，并把完整应用放在实际 **80 MHz** 下完成验证。停止当前试验，是基于已有收益和失败证据作出的工程取舍，并不表示结构已经达到理论极限。

## 十一、时钟约束与板级结果如何写

### 1. 裸 SoC 的频率估计与实际运行点分别列出

99.0589 MHz 是 11.50 ns 目标下，对特定实现得到的报告估计。我们另外施加真正的 10.00 ns 目标进行试验，最高报告估计为 99.5322 MHz，但建立时间仍差 0.047 ns，因此最终没有宣称通过 100 MHz。

完整板级工程包含实际引脚、PLL 和应用接口，布局条件与裸 SoC 不同，结果如下：

| 板级配置 | 目标周期 | 报告 Fmax | 建立时间裕量 | 采用情况 |
|---|---:|---:|---:|---|
| PLL 100 MHz 试验 | 10.00 ns | 94.5626 MHz | −0.575 ns | 未采用 |
| PLL 90 MHz 单次试验 | 约 11.1111 ns | 89.9838 MHz | −0.002 ns | 未采用 |
| PLL 80 MHz 完整应用 | 12.50 ns | 83.3820 MHz | +0.507 ns | 保留并上板验证 |

板级 80 MHz 的实际时钟关系为：

```text
板载 50 MHz 晶振 → PLL 按 8/5 倍频 → 80 MHz CPU 时钟
```

完整应用资源为 **4224 LUT、2858 FF、268 分布式 RAM、4 APM、64 DRM、1 PLL、13 个 I/O**。

### 2. 约束工作的内容

- 描述真实 50 MHz 输入时钟和 PLL 80 MHz 派生关系。
- 按板级连接设置引脚、电平及输出驱动。
- 对异步按键和串口入口，结合实际同步处理设置入口例外。
- LED、串口发送按实际接口性质设置输出传播预算，当前采用 20 ns。
- CPU 内部需要在一拍内完成的通路继续接受正常时序检查。

完整应用已完成真实 RS485 正常通信、故障诊断及超过 10 分钟连续运行；告警 LED 的亮起、清除后熄灭也已进行实物确认。

### 2. 如果继续做，先做什么

| 优先级 | 工作 | 依据与采用标准 |
|---|---|---|
| 第一 | 冻结完整应用，重新归类最慢路径 | 实际上板目标已包含 PLL、固件和引脚，应先确认限制来自哪里 |
| 第二 | 检查取指末级驱动与 RAM 负载位置 | 最终末段地址连接为 2.059 ns，已有明确连线证据 |
| 第三 | 同时检查预测查询地址与标签连接 | 与最慢路径只差 0.004 ns，避免只优化一条链 |
| 第四 | 有明确位置依据时，小范围调整驱动或优先布线 | 比较端到端延迟、全局建立裕量及慢快角保持裕量 |
| 再往后 | 重新考虑预测查询分级或其他结构改变 | 先测周期代价，再判断所需频率是否有可能达到 |

例如，若新方案仍然付出已经测得的 2.11% 周期代价，要胜过 99.0589 MHz 的保留结构，频率至少需要超过约 **101.15 MHz**，才有同任务耗时上的净收益。

适合在报告中保留的主线是：我们先解决存储器读出后的长依赖，再让前递、异常和取指控制提前准备或减少重复门控；当多个路径接近且连线成为主要耗时后，转向固定结构下的物理优化。最终获得可复现的改善，并以程序周期和完整应用验证决定保留哪些修改。
